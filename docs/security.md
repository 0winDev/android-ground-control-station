# Security checklist (OWASP MASVS)

A checklist **inspired by** the [OWASP Mobile Application Security Verification Standard
(MASVS)](https://mas.owasp.org/MASVS/) v2, adapted to GCS. It is not an audit or a certification.
It is filled in as phases land (most items belong to v0.6 Link security and v1.0); the
`safety-reviewer` agent updates it when a PR changes an item's status.

Status: ✅ done · 🚧 in progress · ⏳ pending · ➖ not applicable (with reason)

## Threat model (summary)

- **Assets:** the vehicle's control link (commands, missions), the MAVLink signing key, mission data,
  flight logs (.tlog).
- **Main threats:** spoofed or replayed MAVLink packets on the UDP link; malformed packets crashing
  or stalling the app; leakage of the signing key; operator mistakes (dangerous command sent by
  accident, mission outside limits).
- **Out of scope:** link encryption (provided by the radio in real systems — MAVLink signing
  authenticates but does not encrypt), the vehicle's own security, physical device compromise.

## MASVS-NETWORK

| # | Control | Phase | Status | Evidence / notes |
|---|---|---|---|---|
| N-1 | The UDP endpoint (port, expected vehicle) is configurable; traffic from unexpected system IDs is visible and never merged into the current vehicle. | v0.1 | 🚧 | Port injectable (`UdpTransport`, REQ-005). The first vehicle heard is pinned as the active one and never replaced (#13, `DefaultVehicleRepository.activeSystemId`, REQ-020); other system IDs are kept apart per sysid and shown as an "other vehicle detected" warning in the HUD. **Known limitations until signing (v0.6):** the pin is unauthenticated, so whoever sends the first HEARTBEAT is pinned until the app restarts and the real vehicle then shows only as "other vehicle"; "never merged" holds per system ID only, since a HEARTBEAT with the active system ID from any host is merged (see N-2). If the active vehicle's HEARTBEATs arrive by two routes (direct and through a forwarder), the GCS HEARTBEAT follows whichever came last (#14). **Missing:** an operator setting for the port and the expected vehicle (which also fixes that route flip), and operator selection or confirmation of the active vehicle. |
| N-2 | Link loss is detected (HEARTBEAT timeout) and blocks commands. | v0.1 / v0.4 | 🚧 | HEARTBEAT-timeout detection per system ID done (#12, `DefaultVehicleRepository`, fails safe to LOST if the watchdog stops); while observed, a failed transport is reopened by itself with a bounded backoff (1–5 s); the watchdog does not depend on it, so the vehicle still goes LOST on time and stays LOST until heard again; during the outage the GCS HEARTBEAT is not sent (`NotOpen`) and after reopening it resumes only while the vehicle is still within its timeout; a failure to bind the port on the session's first attempt (another app holds it) is not retried (#25, REQ-019); a reopened link counts as recovered only after a socket has worked for 10 s (twice the maximum backoff, on an injected monotonic clock): until then it is Recovering, the backoff keeps growing instead of restarting, the outage is logged once and the HUD shows the vehicle as usual (CONNECTED or LOST from the watchdog) with a caution "link unstable" warning, so a flapping link no longer floods logcat or flickers; Recovering is held without datagrams for at most 10 s (the backoff wait or a reopened socket that stays silent, as in airplane mode), then the link is Failed again, so a silent link is never shown as merely unstable for long; the link-lost emergency never waits for any of this, since it comes from the HEARTBEAT watchdog; the watchdog's clock (the pipeline's, #71) never runs ahead of the device across a replay, so a live vehicle still goes LOST 3 s after its last HEARTBEAT once a replay has ended (`PipelineClockTest`, `ReplayPipelineTest`, checked in SITL); a port taken while reopening is retried and shown as such, apart from a first-bind failure (#31, REQ-019). **Known limitation:** a pattern that alternates sockets that fail before any datagram with sockets that deliver some can still alternate the HUD between link error and unstable, at most at the backoff rate (1 to 5 s, never reset while unstable); the 10 s hold is a coroutine delay, which does not count device sleep, so after a sleep the change to Failed can come late (the watchdog still goes LOST on the current age); operator warning: link-lost emergency in the HUD, full-screen until #73 and since then a banner that stays the dominant element over the map (#13, #73, `HudViewModelTest`, SITL check against QGroundControl); GCS HEARTBEAT checked in SITL through `tools/sitl/sitl_relay.py` (#14); commands blocked while LOST (#98, REQ-043). **GCS HEARTBEAT (#14, REQ-021):** sent only while the active vehicle is CONNECTED (watchdog and rule on the current age, so a watchdog timer delayed by sleep cannot keep it going; tested). Before this, the vehicle never heard a GCS, so its GCS failsafe stayed inactive ("if no GCS is ever connected, the GCS failsafe will remain inactive regardless of parameter settings", ardupilot.org `gcs-failsafe.html`); with it, the failsafe can act on this app. It acts only if `FS_GCS_ENABLE` is set (ArduCopter's default is 0, disabled, `ArduCopter/Parameters.cpp`) and the vehicle is armed, after `FS_GCS_TIMEOUT` (default 5 s) without this HEARTBEAT; when this GCS stops hearing the vehicle it stops announcing itself, so the failsafe also covers a downlink-only loss. **Known limitations:** (1) after the app is hidden (background or locked screen) the HEARTBEAT stops within seconds: on the API 36 emulator the system blocks the app's network after about 5 s (`sendto` fails with `EPERM`, measured in the #14 SITL check), and the app itself closes the link about 10 s after the HUD is hidden (5 s HUD stop timeout + 5 s link stop timeout). An armed vehicle with the failsafe enabled then triggers it `FS_GCS_TIMEOUT` later; a foreground service is planned before real hardware (#28, v0.4). (2) An uplink-only failure (sends fail while receiving works) is only logged: the HUD stays CONNECTED while the vehicle stops hearing this GCS (#29, v0.4). (3) Arrival time is marked when a datagram is read, so HEARTBEATs that waited in the socket buffer while the device slept look fresh on wake and can bring back up to one timeout of CONNECTED (#12). (4) Until signing (v0.6), what counts as "alive" is not authenticated and the source address is not checked, so any host that reaches UDP 14550 can keep a vehicle CONNECTED with a forged unsigned HEARTBEAT (system 1, component 1); and the GCS HEARTBEAT goes to the address of the active system ID's last HEARTBEAT, so a forged HEARTBEAT with that system ID redirects ours to the forger (any host, a negligible 21-byte/s reflection); the telemetry requests (#36) go to the same address, so a forger also receives seven 45-byte COMMAND_LONGs per connection, and a forged unsigned COMMAND_ACK from that address can hide a rejection. Harmless for telemetry rates. See C-1, A-2. **Commands (#98, REQ-042, REQ-043, ADR 0008):** they do not inherit this: they go only to the address of the active vehicle's first live HEARTBEAT in the session and are not sent while its HEARTBEATs come from another one, nor while LOST, to another system ID or during a replay, checked under the sender's lock before every attempt; an ACK counts only from that address, system ID and component 1, naming the command and addressed to this GCS (`CommandRouteTest`, `GcsMessageSenderTest`, `DefaultCommandRepositoryTest`). A take off (#99, REQ-044) also needs the HEARTBEAT to show the vehicle armed and both its landed state and its position to show it on the ground, checked the same way before each of its two steps, and sends NAV_TAKEOFF only once a HEARTBEAT shows GUIDED; a forged unsigned HEARTBEAT from the pinned address can still fake both until signing. **Known limitations:** until signing, whoever sends the first HEARTBEAT owns the route (N-1), and a forged unsigned ACK from it can fake an answer; a change of the vehicle's address within a session (a router restart, the two routes of N-1, or a forger with its system ID, who can so deny RTL and land from this app while the vehicle's own `FS_GCS` still works) blocks every command until the session ends, so #105 is mandatory before any real flight; another GCS behind the same forwarder answers as 255/190 too, so its ACKs pass as this app's, which signing does not change either. **Telemetry requests (#36, REQ-023):** `MAV_CMD_SET_MESSAGE_INTERVAL` only to the active system ID's autopilot (component 1), only on each change to CONNECTED (first contact and every recovery), one request at a time, never while LOST (a round in progress is cancelled); at most seven frames per LOST → CONNECTED cycle, which needs a full timeout. A missing ACK is not retried, unlike the command protocol ("If no acknowledgement is received the command must be automatically re-sent", mavlink.io `command.html`); the command service with retries comes in v0.4. **Requested again (#39, REQ-023):** a stream silent for its staleness threshold (0.5–3 s) is requested again, at most once every 5 s per stream (a 45-byte COMMAND_LONG, 9 B/s for a stream the vehicle never sends), only while the active vehicle is CONNECTED and heard right now: the link listened to (otherwise waiting for the ACK would open the socket again for nobody) and its HEARTBEAT younger than the timeout on the current age (so not after sleep before the watchdog catches up); both tested. In the SITL check the API 36 emulator blocked the hidden app's network about 5 s after HOME, while the link was still listened to: the streams went silent, two requests were attempted and failed with `EPERM` (`NotSent`, logged once), and nothing reached the vehicle. **Telemetry (#39, REQ-026):** kept per system ID from the autopilot component only, never merged across system IDs; like HEARTBEATs, it is attributed by system ID alone, whatever the source address, and unsigned until v0.6, so a forger (or a second route, #14) with the active system ID can feed it values that read fresh. The staleness rule only says how old a value is, never that it is genuine. **Landed state (#112, REQ-052):** on the ground only on an ON_GROUND from the autopilot younger than 0.5 s, requested at 4 Hz (`LandedRule`), never when unknown, missing or older; it says nothing about the link or the route, which a take off takes from REQ-043; like HEARTBEATs (limitation 3), frames that waited in the socket buffer while the device slept look fresh on wake; like the rest of the telemetry it is unsigned until v0.6, so a forger with the active system ID can make a flying vehicle read as on the ground and let a take off's mode change to GUIDED (#99) through. |

| K-1 | The MAVLink parser never crashes on malformed input (fuzz-style tests). | v0.1 | ⏳ | Related (#12): an *unexpected* exception in the link-loss watchdog is not swallowed. It first marks every vehicle LOST and stops the listener, then crashes the process on purpose. |
| K-2 | Inputs from the network are validated before use (lengths, ranges, enums). | v0.1 | ⏳ | COMMAND_ACK (#36): taken as the answer to a telemetry request only if it comes from the vehicle's system ID, its autopilot component and its address, names `MAV_CMD_SET_MESSAGE_INTERVAL`, is addressed to this GCS (255/190, or 0/0 when the sender omits the extension fields) and carries a final result (`MAV_RESULT_IN_PROGRESS` is skipped). The ACK does not say which message it answers, so a late one is taken as the next request's answer; only `result` is read, never `progress`. Not authenticated until signing (v0.6). Telemetry (#39, `TelemetryMapper`): every documented "unknown" value maps to no value, never to 0, and so do zero-filled accuracies and a `battery_remaining` outside 0–100; ArduPilot's `voltage_battery` 0 (no battery monitor) maps to no value too, so the alerts of #41 must treat a missing reading as unknown, never as OK. Values out of their documented range map to no value too, never clamped or wrapped (#49, REQ-031): `hdg` and `cog` above 35999, GPS `yaw` above 36000, `throttle` above 100, ATTITUDE angles past ±π (compared as float32, so a real ±π reading is kept), and NaN or infinite floats; a latitude past ±90° or a longitude past ±180° (WGS84, since the XML gives no range) drops the whole frame, so the last valid position keeps its time and goes stale rather than vanishing (a bad frame must not clear the stale alert). ArduPilot sends GLOBAL_POSITION_INT whether or not its AHRS has a position (0°, 0° before it ever had one, the last one frozen after losing it: "we send stale data", `GCS_Common.cpp`), so the HUD shows a position as current only with a fresh 3D GPS fix and never at exactly 0°, 0°, and greys it as not verified otherwise (#42, `isPositionVerified`). A 3D GPS fix is the driver's status, not the EKF's: a position frozen while the GPS keeps its fix is not caught, nor is navigation without GPS (optical flow, visual odometry), which shows as not verified; the EKF's own EKF_STATUS_REPORT, in `ardupilotmega.xml` rather than `common.xml`, would be the right source (future issue, v0.4 or later). The height above home is never frozen (`get_relative_position_D_home`: EKF, or barometer or GPS height before an origin). Without a velocity estimate ArduPilot sends 0 for the GLOBAL_POSITION_INT velocities and the VFR_HUD climb rate, which the HUD cannot tell from a real 0. Fields with no documented range (velocities, altitudes, `eph`, `epv`, `vel`, satellites, current) are taken as sent. Alerts (#56): a battery monitor that is enabled but not healthy and has no voltage reading, as at boot, is played down to "battery unknown" only while the vehicle's HEARTBEAT says it is disarmed and it was not already an emergency. That armed bit is not authenticated until signing (v0.6), so a spoofed "disarmed" HEARTBEAT could turn such a battery emergency into an advisory before it is first raised. |
